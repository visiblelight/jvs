## 4. 阶段 2：数据隔离与上传安全

### 4.1 关联对象归属

- 在 service 层统一校验事项 `category_id`、`tag_ids`，新闻 `category_id`、`source_id`，以及分类的 `parent_id`；创建和编辑都使用同一校验逻辑。
- 不存在和不属于当前用户的关联对象统一返回 404，不暴露对象实际归属。超级管理员管理自己的业务记录时也遵循同样规则，不新增跨用户数据访问能力。
- 标签列表先去重；只要包含无权关联的标签就拒绝整个请求，不再静默忽略。失败请求不产生部分更新。
- 分类移动拒绝自身作为父级、循环引用和跨用户父级；显式 `parent_id: null` 可移动为根分类。
- 区分字段未提供与显式 `null`：新闻分类、来源等可选字段允许清空，非空字段拒绝 `null`。不再笼统跳过所有 `None`。
- 对已有跨用户关联提供只读检查。读取接口先屏蔽错误关联对象的名称和详情；修复脚本输出记录 ID 与拟解除的关联，保留内容和主记录，不默认删除数据。生产修复基于报告执行。

### 4.2 图片内容校验与安全访问

- 头像与通用图片上传共用校验函数：保留 2 MB / 5 MB 限制，以受限读取方式处理体积，使用图片解码器（拟采用 Pillow）验证真实格式、完整性和像素大小。
- 支持现有 JPEG、PNG、GIF、WebP；拒绝 HTML、SVG、损坏文件、伪造 MIME 和超出资源限制的图片。扩展名及响应 MIME 由实际图片格式决定，不能由原始文件名决定。
- 新头像使用服务器生成的安全文件名。新文件验证并写入成功、数据库更新成功后再清理旧头像；失败时保留原头像并清理临时文件。
- 保持原有 `/uploads/...` URL 结构，对上传目录实行图片扩展名白名单及 `nosniff`。应用直接访问和 nginx 代理访问都执行相同约束，非图片扩展名不再作为可执行页面提供服务。
- 扫描已有头像及上传目录，列出非允许扩展名、内容与格式不符的文件。先禁止公开访问，不自动清空上传目录；确需隔离文件时保留可追踪备份。
- 将新依赖纳入阶段 6 的锁定安装流程，不做无关依赖升级。

### 验收

- 两个普通用户互相引用分类、来源、标签和父分类均失败；自己的合法关联保持可用。
- 分类不能形成环，移到根分类成功；清空可选新闻字段成功。
- 伪装为 PNG 的 HTML 上传失败；历史 `.html` 上传路径无法以 HTML 访问。
- 合法四种格式正常显示，超限、损坏、无文件名等输入有明确错误响应；上传失败不会丢失旧头像。
- 原有 Markdown 图片、移动端头像、通过代理访问的图片正常工作。

主要文件：`backend/app/api/admin/{todo,news,auth,uploads}.py`、`backend/app/services/{todo,news}.py`、相关 schemas、`backend/main.py`、`nginx/*.conf.template`、上传和数据隔离测试。

## 5. 阶段 3：统一事项状态和删除语义

### 5.1 状态转换

普通编辑 `PUT /items/{id}` 与快捷操作 `PATCH /items/{id}/status` 共用 service 层校验。Schema 共用状态枚举，拒绝未知值和显式 `null`。

| 当前状态 | 允许目标状态 |
| --- | --- |
| pending | pending、paused、completed |
| paused | pending、paused、completed |
| completed | pending、paused、completed、archived |
| archived | archived、completed |

- 同状态提交视为幂等操作，不重写完成或归档时间。
- 首次完成写 `completed_at`；从已完成回到未完成或暂停时清空；归档保留完成时间并设置 `archived_at`；取消归档回到 completed 并清空归档时间。
- 不允许通过普通编辑绕过归档限制。发现历史未知状态只报告，不擅自推断为某个合法状态。

### 5.2 删除及可见性

- 保留当前数据保留设计：删除设置 `is_deleted/deleted_at`；“永久删除”设置 `purged_at`，不改为数据库硬删除。
- 普通列表、日历、详情、编辑、状态修改及评论接口统一排除 `purged_at` 非空的记录；评论修改和删除也必须检查父事项。
- 回收站列出所有未二级删除的 `is_deleted=true` 事项，包括先归档再删除的事项，避免被默认归档过滤隐藏。
- 一级删除记录可在回收站读取用于恢复，但禁止编辑、改状态和增改评论；恢复仅面向未二级删除的记录。
- 二级删除仅接受回收站事项或归档事项，保留现有归档面板的直接永久删除入口；普通活跃事项不能跳过正常流程被二级删除。
- 二级删除后，详情、恢复、编辑、评论和再次删除统一返回 404。列表和评论读取均不得重新暴露记录。

### 验收

参数化验证全部状态转换及 PUT/PATCH 一致性；重复保存不改变时间；一级删除、恢复、归档后删除、二级删除及其所有旁路接口均符合上述规则。现有管理端与移动端正常编辑不受影响。

主要文件：`backend/app/schemas/todo.py`、`backend/app/services/todo.py`、`backend/app/api/admin/todo.py`、两端事项表单与回收站相关页面、`backend/tests/test_todo.py`。

## 6. 阶段 4：统一时间处理，修复“刚创建却早了数小时”

### 6.1 明确两种数据语义

| 类型 | 示例 | 约定 |
| --- | --- | --- |
| 时间点 | created_at、updated_at、due_date、scheduled_at、published_at、ticked_at，以及完成／归档／删除／授权时间 | 统一 UTC 存取，API 返回带 `Z` 或 `+00:00` 的 ISO 8601；界面转换为浏览器本地时间 |
| 业务日期／周期 | start_date、end_date、daily/weekly/monthly 的 period_key | 保持日期或周期字符串，不附加 `Z`，不作为 UTC 时间点自动换日 |

拟新增 `BUSINESS_TIMEZONE`，默认 `Asia/Shanghai`，用于打卡“今天”、周和月边界。普通时间点仍按浏览器本地时区显示；打卡页面明确标明周期所用时区。先采用系统统一业务时区，不引入个人设置。此默认值作为本计划的一部分供用户确认。

### 6.2 后端存取与接口

1. 新建统一 UTC 时间类型及辅助函数。优先保持现有数据库列为不带时区的 timestamp：写入前将 aware datetime 转成 UTC 并去掉时区存储，读取后明确附加 UTC。避免依赖 PostgreSQL 会话时区、宿主机时区或 SQLite 的隐式行为。
2. 将所有表示时间点的 ORM 字段接入该规则；普通 `Date` 字段不改。正常情况下无需批量改列或改历史值，Alembic 必须验证没有非预期结构差异。
3. API 时间点输出全部明确带时区，涵盖嵌套分类、来源、评论、用户、Access Key、打卡统计与开放接口；不能只修事项详情某一个字段。
4. 对客户端可写入的时间点及日历查询边界要求带时区，统一归一化为 UTC；无时区 datetime 返回 422，错误信息说明需提供 `Z` 或偏移量。当前两端表单已使用 `toISOString()`，外部新闻提交调用方需按更新后的文档验证兼容性。
5. 空值仍为 `null`；纯日期仍为 `YYYY-MM-DD`。内部历史无时区值仅在已确认 UTC 存储语义的读取边界解释为 UTC，不能将所有外部无时区输入静默当成本地时间。

### 6.3 前端展示与表单

- 两端分别集中封装日期解析、时间点格式化、相对时间及 `datetime-local` 回填函数；本次不为复用少量函数建立新的跨项目包。
- 创建时间、评论“刚刚”、完成／归档／删除时间、新闻日期、个人资料及打卡时间统一使用上述函数。
- 本地表单输入转 ISO 时间点提交；带时区 API 值转成本地年月日时分后回填。打开编辑、直接保存、再次打开必须保持同一个时间点。
- 日历查询以显示时区的日期边界构造带时区时间点，再转换为 UTC，使用左闭右开区间。日期字符串不使用 `new Date('YYYY-MM-DD')` 后再按本地字段取值的混合方式。
- 兼容分阶段发布：过渡解析函数仅对已知时间点字段的旧无时区响应按 UTC 解释，不能对纯日期或用户输入盲目补 `Z`。新 API 契约稳定后统一依赖带时区返回。

### 6.4 历史数据与上线保护

- 发布前只读核验 PostgreSQL 列类型、会话时区、时间写入来源及可与实际事件对应的样本。系统生成时间与用户输入时间分别检查。
- 已确认按 UTC 存储的值保持原样，只修解释和传输。禁止给整库时间统一加／减 8 小时。
- 若存在历史本地时间与 UTC 混存，按表、字段、来源生成只读清单和修复映射；无法判断的记录不自动变更。修复前保存旧值，确保可回滚，不擅自根据“看上去差 8 小时”改数据。
- 第 4 阶段先交付时间点契约与展示修复；打卡业务日期切换与历史 period_key 处理放在第 5 阶段一起发布，避免只改日期判断而留下不兼容的历史周期。

### 6.5 验收场景

- 固定时钟：UTC 05:00 创建事项，上海界面显示 13:00；立即创建的评论显示“刚刚”。刷新、重新登录和移动端查看结果一致。
- 同一时间点使用 `Z`、`+08:00` 输入得到相同存储与显示；无时区写入得到可读的 422。
- 上海 00:30 新建事项属于本地当天；日历起止边界不漏项、不跨格。
- 截止时间、执行时间、新闻发布时间连续编辑保存两次不累积偏移。
- UTC、Asia/Shanghai 及带夏令时的浏览器时区验证格式化和日期边界；打卡业务日期始终遵循配置时区。
- SQLite 和 PostgreSQL 的时间往返结果一致；改变 PostgreSQL 会话时区不会改变新写入的时间点。
- 历史纯日期和任务开始／结束日期不发生平移。

主要文件：拟新增 `backend/app/core/datetime.py` 或等价公共模块、`backend/app/core/config.py`、models 与 schemas、两端时间工具及各时间展示／表单组件、日历查询、时间专项测试。

## 7. 阶段 5：打卡周期、补录和跨天行为

### 7.1 周期校验与业务日期

- 所有创建打卡、撤销、任务状态统计及补打卡的“今天”统一通过阶段 4 的业务时区辅助函数取得；一请求使用同一个基准时刻，避免跨午夜时多次取 now 产生矛盾。
- period_key 严格匹配任务频率：日为有效 `YYYY-MM-DD`，周为有效 ISO 周 `YYYY-Www`，月为有效 `YYYY-MM`。检查真实日历有效性，不能只用正则或字符串大小比较。
- 补录周期必须早于当前业务周期；且对应周期与任务有效日期区间有交集，起止日期均包含。日频率等价于该日在区间内；周、月任务允许起止日期所在的不完整周期。
- 已归档任务不能补录；已结束但未归档的任务可补录其有效区间内的历史周期。
- 保留 Plan 023 的积分规则：补录固定 0 分，不追溯改历史积分，后续连续周期自然接续。
- 并发重复打卡由唯一约束兜底，捕获约束冲突并回滚事务，返回与现有重复打卡一致的 400，而不是 500。

### 7.2 查询与字段更新

- 区分 `ticked_at`（实际提交时间）与 period_key（业务所属周期）。补录的实际提交时间保留，不伪装成历史提交。
- 日历按业务周期查询：日频率以目标日、周频率以该周周日、月频率以月末作为既有日历补录落点；普通打卡以提交时间在业务时区中的日期展示。
- 周／月完成态按 period_key 匹配，查询需包含与展示范围重叠的周期，不能只按实际提交时间截取。日志列表仍显示实际提交时间，另显示补录目标周期。
- 明确日历用查询的参数语义；可为 `/tick/logs` 增加 `date_basis=calendar|submitted`，默认保留 submitted 语义，管理端日历显式使用 calendar，避免悄悄改变其他调用方。
- `TickTaskUpdate` 使用 `exclude_unset` 区分未提供和清空：description、end_date 可显式清空；非空字段不接受 null。增加起止日期与积分阶梯结构校验，避免在计算积分时出现 KeyError 等内部异常。
- 已产生记录的任务禁止直接修改 frequency，返回明确业务错误；更换频率通过新任务进行，防止旧 period_key 被另一种频率解释。

### 7.3 历史周期兼容

- UTC 改为 Asia/Shanghai 划日会影响凌晨记录，也可能改变跨周、跨月归属，不能只换一行“今天”的计算。
- 实施时提供 dry-run：普通记录用原始 UTC ticked_at 推导新业务周期；补录记录保留明确指定的 period_key，并校验其合法性。输出旧／新 key、任务 ID、冲突及超出任务有效日期的记录。
- 无冲突的普通记录可在维护窗口中按审核后的映射事务性更新，保存旧 key；补录积分及历史 points_earned 不重算。连续次数允许按校正后的实际周期重新计算，并说明可能变化。
- 若同一任务出现新周期冲突、非法历史补录或无法确认的时间来源，禁止自动覆盖、合并或删除。输出具体清单，在处理规则确认前不切换生产业务时区；其他不依赖周期切换的修复可先发布。
- 切换时短暂停止打卡写入，备份数据库，完成映射与校验后启用新版本，避免新旧规则同时写入。回滚必须同时恢复周期映射和配置，不只是回退代码。
- 业务时区在投入使用后不作为随意修改的普通配置；再次变更需走同样的数据兼容流程。

### 7.4 跨天刷新与查询开销

- 管理端及移动端统一处理下一次业务午夜的刷新，并保留页面恢复可见时的补偿检查。一直停留在前台的页面也应刷新，不能只依赖 visibilitychange。
- 服务端向登录客户端提供业务时区信息（如 `/auth/me` 增加 `business_timezone`），前端据此显示日期及计算刷新时刻；销毁页面时清理定时器，避免重复请求。
- 提取任务统计／周期辅助逻辑；连续次数按批量加载的周期集合计算，避免每个连续周期单独访问数据库。不扩展为全面性能重构。
