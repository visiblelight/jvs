# Plan 024 发布前核验与回滚

本说明供后续获准发布时使用；代码修复不自动触发下列生产操作。

## 时间数据核验

确认 PostgreSQL 当前 `SHOW TIME ZONE`、列类型、应用写入来源，抽取能与实际事件核对的时间样本，区分系统生成时间与外部输入。确认原 timestamp 值表达 UTC 后，可直接使用新 UTCDateTime 类型，不移动存储值。发现混存时先形成逐条映射，不能全库加减 8 小时。

HTTP 时间点输入今后要求 Z 或偏移量，先验证外部新闻提交调用方。检查可空历史时间是否为真实缺失；不要用发布时间或当前时间伪造创建时间。

## 关联和上传检查

在 backend 目录运行只读检查，将输出保存在安全位置：

```bash
python -m scripts.audit_integrity --uploads uploads > /safe/location/integrity-report.json
```

输出包括错误跨用户关联的 ID、旧关联及拟解除操作，未知事项状态，以及非法上传文件清单。脚本不修改记录或文件。新接口先屏蔽错误关联，上传服务拒绝非图片；数据修复／文件隔离应根据报告审核，先备份，不删除主记录或整目录。

## 打卡历史周期切换

1. 备份数据库和上传文件，在独立临时库验证备份可恢复。恢复现有非空库前先制定清理或换库流程，不能把普通 pg_dump 直接导入非空库当成可靠回滚。
2. 在旧系统仍运行时可先生成预演报告；正式切换时停止所有打卡写入，再生成最终报告。
3. 使用新代码的工具（在 backend 目录）预演：

```bash
python -m scripts.migrate_tick_timezone --timezone Asia/Shanghai > /safe/location/tick-report.json
```

普通记录由原 UTC ticked_at 推导上海周期；补录保留指定周期。报告包含原始快照、旧／新 key、冲突及无效日期。工具不平移 ticked_at，不重算历史积分。

4. 审核报告。存在冲突、越界周期或错误归属时，工具拒绝应用；先明确每条记录的处理方式，不自动合并、覆盖、丢弃。冲突解决前不启用新周期规则。
5. 确认报告与时间来源后，在写入停止的维护窗口应用：

```bash
python -m scripts.migrate_tick_timezone --apply /safe/location/tick-report.json
```

工具锁定数据、核对完整快照、在同一事务中更新 key；快照过期或映射被改动时拒绝。保留报告及数据库备份。修改只影响业务周期和按周期计算的连续次数，不更改已获积分。

6. 设置 BUSINESS_TIMEZONE=Asia/Shanghai，发布前后端，核验普通打卡、补录、日历与跨天行为后恢复写入。

## 回滚

若尚未恢复写入，可运行 `--restore /safe/location/tick-report.json` 还原周期映射，再恢复旧代码和时区配置。若切换后已有新日志、积分或任务日期变化，工具会拒绝直接恢复；此时需基于备份与新写入数据形成专门恢复方案，不能只回退代码或强行覆盖日志。

本次修复不执行部署、备份恢复或真实历史数据修改。历史数据核验和周期映射不由 CI 或应用启动自动执行；数据库结构升级仍使用 Alembic。现有 CI 在 main 推送且全部检查通过后会部署，因此周期数据切换须先按本说明单独审核和安排维护窗口，再允许推送触发发布。
